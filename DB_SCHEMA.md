# Database Schema

The application uses an embedded, file-based **H2** database (`demo1db.mv.db`).
Hibernate auto-generates and updates this schema on application startup
(`spring.jpa.hibernate.ddl-auto=update`). The file is opened with
`AUTO_SERVER=TRUE`, so a SQL client can attach to the same file while the
application is running.

Column types below are the **actual DDL Hibernate 7.4.5 generates for H2**
(`org.hibernate.dialect.H2Dialect`), captured from the startup log. Note that the
types are dialect-specific , a different database would produce different
column definitions for the same entities.

```sql
create table products (
    price       numeric(19,2) not null,
    stock       integer,
    id          bigint generated by default as identity,
    version     bigint not null,
    description varchar(255),
    name        varchar(255) not null,
    primary key (id)
)

create table orders (
    id         bigint generated by default as identity,
    order_date timestamp(6) not null,
    status     enum ('CANCELLED','COMPLETED','PENDING') not null,
    primary key (id)
)

create table order_items (
    quantity   integer not null,
    unit_price numeric(19,2) not null,
    id         bigint generated by default as identity,
    order_id   bigint not null,
    product_id bigint not null,
    primary key (id),
    constraint uk_order_product unique (order_id, product_id)
)

alter table if exists order_items
    add constraint FKbioxgbv59vetrxe0ejfubep1w foreign key (order_id) references orders
alter table if exists order_items
    add constraint FKocimc7dtr037rh4ls4l95nlfi foreign key (product_id) references products
```

## Tables Overview

### 1. `products`

Stores product catalog information.

| Column | Type | Constraints | Description |
| --- | --- | --- | --- |
| `id` | `bigint` | PRIMARY KEY, `generated by default as identity` | Unique product identifier |
| `name` | `varchar(255)` | NOT NULL | Product name |
| `description` | `varchar(255)` | *(nullable)* | Optional description. See the length warning below |
| `price` | `numeric(19,2)` | NOT NULL | Current price of the product. Exact decimal , never a binary float |
| `stock` | `integer` | *(nullable)* | Current **available** stock. May be `NULL` on legacy rows; treated as `0` when an order is placed |
| `version` | `bigint` | NOT NULL | Optimistic-locking version, managed by Hibernate. Starts at `0`, incremented on every update |

> **`description` length mismatch (known, intentionally left in code).** The
> column is `varchar(255)` because the entity declares no `@Column(length = ...)`,
> but `ProductRequest.description` is annotated `@Size(max = 2000)`. A description
> between 256 and 2000 characters therefore passes bean validation and then fails
> at flush time (surfacing as the generic `409` from the
> `DataIntegrityViolationException` safety net). The two possible fixes , adding
> `@Column(length = 2000)` to `Product.description`, or lowering the DTO limit to
> 255 , were deliberately deferred, so keep descriptions under 255 characters.
>
> **`stock` is nullable in the database but required by the API.** `ProductRequest.stock`
> is `@NotNull`, so new products always have a value; the nullable column exists
> only so that rows created before that rule can still be read.

### 2. `orders`

Stores order header information.

| Column | Type | Constraints | Description |
| --- | --- | --- | --- |
| `id` | `bigint` | PRIMARY KEY, `generated by default as identity` | Unique order identifier |
| `order_date` | `timestamp(6)` | NOT NULL | Date and time when the order was created |
| `status` | `enum ('CANCELLED','COMPLETED','PENDING')` | NOT NULL | Order status. See the note below |

> **`status` is a native H2 `ENUM`, not a `varchar`.** The entity uses
> `@Enumerated(EnumType.STRING)`, and Hibernate 7 renders that as a real enum type
> on H2 (values sorted alphabetically). On most other databases the same mapping
> produces a `varchar` column instead, so this is dialect-specific.
>
> Because `ddl-auto=update` only *adds* missing tables/columns, changing the
> `Status` enum later (adding or renaming a value) will not be migrated
> automatically , H2 will reject a value the enum type does not declare. Plan a
> manual `ALTER`/recreate for such a change.
>
> **Status is never updated by the API.** Every order is created as `PENDING` and
> no endpoint changes it, so `COMPLETED` and `CANCELLED` are currently unused.

### 3. `order_items`

Stores line items for an order, mapping a specific product and quantity to an order.

| Column | Type | Constraints | Description |
| --- | --- | --- | --- |
| `id` | `bigint` | PRIMARY KEY, `generated by default as identity` | Unique line item identifier |
| `order_id` | `bigint` | NOT NULL, FOREIGN KEY → `orders.id` | Owning order |
| `product_id` | `bigint` | NOT NULL, FOREIGN KEY → `products.id` | Ordered product |
| `quantity` | `integer` | NOT NULL | Quantity ordered (`>= 1`, enforced by bean validation) |
| `unit_price` | `numeric(19,2)` | NOT NULL | Price snapshot taken at the time of order creation. Exact decimal , never a binary float |

**Constraints:**

- `uk_order_product (order_id, product_id)` , a product may appear only once per order.
  Violating it would otherwise surface as an opaque `409`; `OrderService` detects the
  duplicate earlier and returns a descriptive `400`.
- `FKbioxgbv59vetrxe0ejfubep1w (order_id → orders.id)`
- `FKocimc7dtr037rh4ls4l95nlfi (product_id → products.id)`
- **No index on `product_id` alone.** `uk_order_product` is `(order_id, product_id)`, so it
  cannot efficiently serve `WHERE product_id = ?` (used by
  `OrderItemRepository.countByProductId`). Add an index if that check becomes hot.

## Relationships

- **Product 1 : N OrderItem** , A product can be referenced by many order items.
- **Order 1 : N OrderItem** , An order contains one or more order items
  (`@OneToMany(cascade = ALL, orphanRemoval = true)`). When an order is deleted, its
  `order_items` are removed automatically , visible in the SQL as
  `delete from order_items where id=?` followed by `delete from orders where id=?`.
- **Deleting a product** that is still referenced by any `order_items` row is rejected with
  `409 Conflict` , the foreign key would otherwise be violated. `ProductService.deleteById()`
  checks `OrderItemRepository.countByProductId` first so the client gets an actionable
  message instead of a generic constraint error. Delete the orders first, or keep the product.

```text
products                 orders
   │ id                      │ id
   │ name                    │ order_date
   │ description             │ status
   │ price                   │
   │ stock                   │
   │ version                 │
   │                         │
   └───┐                 ┌───┘
       │ N             N │
       └──► order_items ◄─┘
              id
              order_id      → orders.id
              product_id    → products.id
              quantity
              unit_price
```

## Stock handling

`stock` means **available** stock, not total stock on hand. `OrderService` validates
the whole request before mutating anything, so an invalid request never leaves
stock partially decremented.

- **Create order:** each line item is checked against `products.stock`. A missing
  product, a duplicate `productId`, or insufficient stock returns
  `400 Bad Request`. On success the ordered quantity is subtracted from
  `products.stock`.
- **Delete order:** the quantities consumed by the order are added back to
  `products.stock`.
- **Null stock:** a `NULL` value is treated as `0` (via the `currentStock()` helper), so
  legacy rows cannot cause an NPE (HTTP 500).

The decrement happens through JPA **dirty checking**: the service mutates the managed
`Product` entity and saves only the `Order`; Hibernate issues the
`update products set ... where id=? and version=?` statement on flush.

### Decided behaviour: `PUT /api/products` sets `stock` authoritatively

`stock` is *derived* bookkeeping (orders subtract from it, deletion adds back), and
`PUT /api/products/{id}` overwrites it with whatever value the client sends. The
two rules interact, so stock can end up above the original total. Accepted
sequence, reproduced against a running instance:

```text
stock 10  →  POST /api/orders (quantity 3)  →  stock 7
          →  PUT /api/products (stock=10)   →  stock 10
          →  DELETE /api/orders/{id}        →  stock 13   ← above the original 10
```

The order's reservation was still outstanding when the PUT arrived, so restoring it
adds back a quantity that had already been written off. **This is the intended
semantics of the project, not a defect.** Clients must not overwrite `stock` while
orders are open if they need exact totals.

> **Rejected alternative:** persisting a separate total stock and deriving
> available stock from open orders. It removes the interaction above, but changes
> the entity model, the schema and every reader of `stock`, so the simpler
> "available stock" definition was kept deliberately.

### Concurrency

Because `products.version` is incremented on every update and included in the
`WHERE` clause, two orders racing for the same stock cannot both succeed: the
losing request fails the version check and is reported as `409 Conflict`.

`orders` and `order_items` have **no** `version` column, so concurrent modifications
to an order are not protected by optimistic locking.

## Money handling

`price` and `unit_price` are `BigDecimal` mapped to `NUMERIC(19,2)`, not `double`.
Binary floating point cannot represent decimal amounts exactly, so repeated
arithmetic on prices would slowly drift; decimal arithmetic does not.

`ProductRequest.price` is additionally constrained with
`@Digits(integer = 17, fraction = 2)`, so a value the column cannot hold is
rejected with `400 Bad Request` instead of being silently rounded
(`17 + 2 = 19`, exactly the column's precision).

`OrderResponse.totalPrice` is computed at read time as
`Σ(unitPrice × quantity)` using `BigDecimal` , it is **not** a stored column, so it
can never drift out of sync with the line items.

## Migrations

There is no migration tool (Flyway/Liquibase) in this project. The schema is owned
by Hibernate:

- `ddl-auto=update` (production, `src/main/resources/application.properties`) adds missing
  tables and columns but never drops or alters existing ones. It keeps data between
  restarts.
- `ddl-auto=create-drop` (tests, `src/test/resources/application.properties`) recreates the
  schema for each test context, against an in-memory database.

> **Never set `ddl-auto=create` in `application.properties`.** The database is a
> file-based H2 database, so `create` drops and recreates every table on each
> startup, wiping all products and orders.
