# Database Schema

The application uses an embedded, file-based **H2** database (`demo1db.mv.db`).
Hibernate auto-generates and updates this schema on application startup
(`spring.jpa.hibernate.ddl-auto=update`). The file is opened with
`AUTO_SERVER=TRUE`, so a SQL client can attach to the same file while the
application is running.

Column types below are the **actual DDL Hibernate 7.4.5 generates for H2**
(`org.hibernate.dialect.H2Dialect`), captured from the startup log. Note that the
types are dialect-specific , a different database would produce different
column definitions for the same entities.

```sql
create table products (
    price       numeric(19,2) not null,
    stock       integer,
    id          bigint generated by default as identity,
    version     bigint not null,
    description varchar(255),
    name        varchar(255) not null,
    primary key (id)
)

create table carts (
    id          bigint generated by default as identity,
    updated_at  timestamp(6) not null,
    customer_id varchar(255) not null,
    primary key (id),
    constraint uk_cart_customer unique (customer_id)
)

create table cart_items (
    quantity   integer not null,
    cart_id    bigint not null,
    id         bigint generated by default as identity,
    product_id bigint not null,
    primary key (id),
    constraint uk_cart_product unique (cart_id, product_id)
)

create table orders (
    id         bigint generated by default as identity,
    order_date timestamp(6) not null,
    paid_at    timestamp(6),
    status     enum ('CANCELLED','PAID','PENDING_PAYMENT') not null,
    primary key (id)
)

create table order_items (
    quantity   integer not null,
    unit_price numeric(19,2) not null,
    id         bigint generated by default as identity,
    order_id   bigint not null,
    product_id bigint not null,
    primary key (id),
    constraint uk_order_product unique (order_id, product_id)
)

alter table if exists cart_items
    add constraint FKpcttvuq4mxppo8sxggjtn5i2c foreign key (cart_id) references carts
alter table if exists cart_items
    add constraint FK1re40cjegsfvw58xrkdp6bac6 foreign key (product_id) references products
alter table if exists order_items
    add constraint FKbioxgbv59vetrxe0ejfubep1w foreign key (order_id) references orders
alter table if exists order_items
    add constraint FKocimc7dtr037rh4ls4l95nlfi foreign key (product_id) references products
```

## Tables Overview

### 1. `products`

Stores product catalog information.

| Column | Type | Constraints | Description |
| --- | --- | --- | --- |
| `id` | `bigint` | PRIMARY KEY, `generated by default as identity` | Unique product identifier |
| `name` | `varchar(255)` | NOT NULL | Product name |
| `description` | `varchar(255)` | *(nullable)* | Optional description. See the length warning below |
| `price` | `numeric(19,2)` | NOT NULL | Current price of the product. Exact decimal , never a binary float |
| `stock` | `integer` | *(nullable)* | Physical units on hand. Written by `ProductService` (restock) and `OrderService.pay()` (settled sale). May be `NULL` on legacy rows; treated as `0` |
| `version` | `bigint` | NOT NULL | Optimistic-locking version, managed by Hibernate. Starts at `0` and is incremented by every update, including the stock decrement done by `pay()` |

> **`description` length mismatch (known, intentionally left in code).** The
> column is `varchar(255)` because the entity declares no `@Column(length = ...)`,
> but `ProductRequest.description` is annotated `@Size(max = 2000)`. A description
> between 256 and 2000 characters therefore passes bean validation and then fails
> at flush time (surfacing as the generic `409` from the
> `DataIntegrityViolationException` safety net). The two possible fixes , adding
> `@Column(length = 2000)` to `Product.description`, or lowering the DTO limit to
> 255 , were deliberately deferred, so keep descriptions under 255 characters.
>
> **`stock` is nullable in the database but required by the API.** `ProductRequest.stock`
> is `@NotNull`, so new products always have a value; the nullable column exists
> only so that rows created before that rule can still be read.

### 2. `carts`

One row per customer. There is no authentication yet, so a cart is keyed by the
client-supplied `customer_id` string.

| Column | Type | Constraints | Description |
| --- | --- | --- | --- |
| `id` | `bigint` | PRIMARY KEY, `generated by default as identity` | Unique cart identifier |
| `customer_id` | `varchar(255)` | NOT NULL, UNIQUE (`uk_cart_customer`) | Cart owner. Comes from the URL, e.g. `/api/carts/budi` |
| `updated_at` | `timestamp(6)` | NOT NULL | Last time the cart was modified |

> **A cart row is created on the first write, never by a read.** `GET
> /api/carts/{customerId}` for an unknown customer returns an empty cart without
> inserting anything, so a mistyped customer id cannot litter the table.

### 3. `cart_items`

Line items of a cart. **This table never influences `products.stock`.**

| Column | Type | Constraints | Description |
| --- | --- | --- | --- |
| `id` | `bigint` | PRIMARY KEY, `generated by default as identity` | Unique line identifier |
| `cart_id` | `bigint` | NOT NULL, FOREIGN KEY → `carts.id` | Owning cart |
| `product_id` | `bigint` | NOT NULL, FOREIGN KEY → `products.id` | Product in the cart |
| `quantity` | `integer` | NOT NULL | Quantity in the cart (`1`–`999`, enforced by bean validation) |

**Constraints:**

- `uk_cart_product (cart_id, product_id)` , one line per product. Adding a product
  that is already in the cart therefore *accumulates* into the existing line;
  `CartService.addItem` does this explicitly, because a second row would otherwise
  fail at flush time with an opaque `409`.
- `FKpcttvuq4mxppo8sxggjtn5i2c (cart_id → carts.id)`
- `FK1re40cjegsfvw58xrkdp6bac6 (product_id → products.id)`

> **No price column.** A cart always shows the *live* catalogue price; the price is
> frozen into `order_items.unit_price` only at checkout. That is why a cart total can
> differ from the eventual order total if the product is repriced in between.

### 4. `orders`

Order header. An order is created by a cart checkout and then settled at the cashier.

| Column | Type | Constraints | Description |
| --- | --- | --- | --- |
| `id` | `bigint` | PRIMARY KEY, `generated by default as identity` | Unique order identifier |
| `order_date` | `timestamp(6)` | NOT NULL | When the order was created (checkout) |
| `status` | `enum ('CANCELLED','PAID','PENDING_PAYMENT')` | NOT NULL | Order status. See the lifecycle below |
| `paid_at` | `timestamp(6)` | *(nullable)* | When the cashier confirmed payment; `NULL` while unpaid |

**Status lifecycle:**

```text
checkout  ->  PENDING_PAYMENT  --POST /api/orders/{id}/pay-->  PAID
                    |
                    +--POST /api/orders/{id}/cancel-->  CANCELLED
```

> **`status` is a native H2 `ENUM`, not a `varchar`.** The entity uses
> `@Enumerated(EnumType.STRING)`, and Hibernate 7 renders that as a real enum type
> on H2 (values sorted alphabetically). On most other databases the same mapping
> produces a `varchar` column instead, so this is dialect-specific.
>
> **Changing the enum requires recreating the table.** Because `ddl-auto=update`
> only *adds* missing tables and columns, it will not widen an existing enum type.
> H2 rejects any value the type does not declare, so a renamed or added status
> needs a manual `ALTER` or a table recreate. The current enum was introduced that
> way: `PENDING`/`COMPLETED` became `PENDING_PAYMENT`/`PAID`.
>
> **`PAID` is terminal.** No endpoint moves an order out of `PAID`: it cannot be paid
> again, cancelled, or deleted, so a settled sale always stays in the sales record.

### 5. `order_items`

Line items of an order, mapping a specific product and quantity to an order.

| Column | Type | Constraints | Description |
| --- | --- | --- | --- |
| `id` | `bigint` | PRIMARY KEY, `generated by default as identity` | Unique line item identifier |
| `order_id` | `bigint` | NOT NULL, FOREIGN KEY → `orders.id` | Owning order |
| `product_id` | `bigint` | NOT NULL, FOREIGN KEY → `products.id` | Ordered product |
| `quantity` | `integer` | NOT NULL | Quantity ordered (`>= 1`) |
| `unit_price` | `numeric(19,2)` | NOT NULL | Price snapshot taken at checkout. Exact decimal , never a binary float |

**Constraints:**

- `uk_order_product (order_id, product_id)` , a product appears at most once per
  order. The cart's own unique constraint guarantees this upstream.
- `FKbioxgbv59vetrxe0ejfubep1w (order_id → orders.id)`
- `FKocimc7dtr037rh4ls4l95nlfi (product_id → products.id)`
- **No index on `product_id` alone.** `uk_order_product` is `(order_id, product_id)`,
  so it cannot efficiently serve `WHERE product_id = ?` (used by
  `OrderItemRepository.countByProductId`). The same applies to `cart_items` and
  `CartItemRepository.countByProductId`. Add indexes if those checks become hot.

## Relationships

- **Product 1 : N CartItem** , a product can sit in many carts.
- **Cart 1 : N CartItem** , `@OneToMany(cascade = ALL, orphanRemoval = true)`. Clearing
  a cart removes its lines.
- **Product 1 : N OrderItem** , a product can be referenced by many order items.
- **Order 1 : N OrderItem** , `@OneToMany(cascade = ALL, orphanRemoval = true)`. Deleting
  an order removes its lines , visible in the SQL as
  `delete from order_items where id=?` followed by `delete from orders where id=?`.
- **Deleting a product** that is referenced by any `order_items` **or** `cart_items` row is
  rejected with `409 Conflict`, because both columns are foreign keys.
  `ProductService.deleteById()` checks `OrderItemRepository.countByProductId` and
  `CartItemRepository.countByProductId` first, so the client gets an actionable message
  instead of a generic constraint error.

```text
products                     carts
   │ id                         │ id
   │ name                       │ customer_id
   │ description                │ updated_at
   │ price                      │
   │ stock                      │
   │ version                    │
   │                            │
   ├──┐                    ┌────┤
   │  │ N                N │    │
   │  └──► cart_items ◄────┘    │
   │         id                 │
   │         cart_id   → carts.id
   │         product_id → products.id
   │         quantity
   │
   └──┐                    ┌────── orders
      │ N                N │        id
      └──► order_items ◄──┘        order_date
             id                    status
             order_id   → orders.id
             product_id → products.id
             quantity
             unit_price
```

## Stock handling

`stock` is the **physical count on hand**. Exactly two things write it:

| Writer | Operation | Effect |
| --- | --- | --- |
| `ProductService.create` / `update` | `POST` / `PUT /api/products` | Sets the value verbatim , an explicit restock or stock correction |
| `OrderService.pay` | `POST /api/orders/{id}/pay` | Subtracts the ordered quantities , the only sale-driven write |

**Nothing ever adds stock back.** This is the property that makes the model consistent:

- A cart never reserves anything, so it never needs releasing.
- An unpaid order never deducted anything, so cancelling or deleting it changes no stock.
- A paid order is terminal, so it can never be cancelled or deleted.
- `OrderService.deleteById` and `cancel` therefore contain no stock arithmetic at all.

The invariant `stock = units received - units sold` consequently holds at all times, and
the same units can never be counted twice. The old design broke this: it kept the order's
reservation inside `stock`, and then a `DELETE` added that reservation back on top of a
value a `PUT` had already overwritten, inventing units.

> **Null stock:** a `NULL` value is treated as `0` by `Product.availableStock()`, so legacy
> rows cannot cause an NPE (HTTP 500). The authoritative check is not this helper though ,
> see Concurrency below.

### Two-phase checkout, single-phase payment

`CartService.checkout` validates the whole cart before creating anything, so a rejected
checkout never leaves a half-built order. The availability check there is a **fast-fail
courtesy** so the buyer is told immediately; it is a read and can go stale. The
authoritative check happens at payment, inside the database.

### Concurrency

Settling a sale is one conditional `UPDATE`, executed through
`ProductRepository.decrementStockIfAvailable`:

```sql
update products
   set stock = stock - :quantity,
       version = version + 1
 where id = :id
   and stock >= :quantity
```

`@Modifying` returns the number of affected rows: `1` means the units were settled, `0`
means the database refused because `stock >= :quantity` did not hold at that instant. The
check and the subtraction are a single statement, so two cashiers paying for the last unit
at the same time cannot both succeed , the second blocks on the row lock, re-evaluates the
condition against the committed value and matches nothing. Two tests verify it:
`OrderPaymentFlowTest.concurrentPayments_cannotOversellTheLastUnit()` calls the service from
several threads, and
`CashierFlowEndToEndTest.simultaneousCashiers_overRealHttp_onlyOneWinsTheLastUnit()` sends five
genuinely parallel HTTP requests to a running server.

The order's own status transition is claimed the same way, with a single conditional `UPDATE` on
`orders.status` (`... WHERE id = ? AND status = 'PENDING_PAYMENT'`) issued *before* any stock is
deducted. `OrderPaymentFlowTest.concurrentPaymentsOfTheSameOrder_deductStockExactlyOnce()` runs six
cashiers against one order and asserts that exactly one of them wins and that a one-unit order removes
exactly one unit from stock.

Two further details matter:

- **`version` is bumped by hand.** Without it a concurrent `PUT /api/products/{id}` , a
  read-modify-write guarded by `@Version` , could silently overwrite a settled sale. With
  it, the PUT fails its version check and is reported as `409 Conflict`.
- **Line items are sorted by `product_id` before decrementing**, so concurrent payments that
  share products always request the row locks in the same order and cannot deadlock.

An insufficient-stock failure at payment throws inside the transaction, so every decrement
that already succeeded for that order is rolled back: an order can never end up
half-settled.

`orders`, `order_items`, `carts` and `cart_items` have **no** `version` column, so
concurrent modifications to those rows are not protected by optimistic locking.

## Money handling

`price` and `unit_price` are `BigDecimal` mapped to `NUMERIC(19,2)`, not `double`.
Binary floating point cannot represent decimal amounts exactly, so repeated
arithmetic on prices would slowly drift; decimal arithmetic does not.

`ProductRequest.price` is additionally constrained with
`@Digits(integer = 17, fraction = 2)`, so a value the column cannot hold is
rejected with `400 Bad Request` instead of being silently rounded
(`17 + 2 = 19`, exactly the column's precision).

`OrderResponse.totalPrice` and `CartResponse.totalPrice` are computed at read time as
`Σ(unitPrice × quantity)` using `BigDecimal` , neither is a stored column, so they can never
drift out of sync with their line items.

## Migrations

There is no migration tool (Flyway/Liquibase) in this project. The schema is owned
by Hibernate:

- `ddl-auto=update` (production, `src/main/resources/application.properties`) adds missing
  tables and columns but never drops or alters existing ones. It keeps data between
  restarts.
- `ddl-auto=create-drop` (tests) recreates the schema for each test context. The four in-memory
  test classes use `src/test/resources/application.properties` against `jdbc:h2:mem:demo1test`,
  while `CashierFlowEndToEndTest` uses the `e2e` profile
  (`src/test/resources/application-e2e.properties`) against a file-backed
  `jdbc:h2:file:./target/e2e-db`. Both drop and recreate at startup, so neither depends on the
  state a previous run left behind.

> **Never set `ddl-auto=create` in `application.properties`.** The database is a
> file-based H2 database, so `create` drops and recreates every table on each
> startup, wiping all products and orders.
>
> **Upgrading from a database created before the cart feature.** `carts` and `cart_items`
> are new tables, so `update` creates them automatically. The `orders` table is different:
> its `status` column is a native `ENUM` whose values changed from
> `('CANCELLED','COMPLETED','PENDING')` to `('CANCELLED','PAID','PENDING_PAYMENT')`, and
> `paid_at` was added. `update` will add `paid_at` but will **not** widen the enum type, so
> an existing database will reject the new status values at runtime. Delete
> `demo1db.mv.db` (losing all data) or drop `orders` and `order_items` by hand before
> starting the new version.
